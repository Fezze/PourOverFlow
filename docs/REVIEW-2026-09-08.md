# Project review — 2026-09-08

The review focused on phone/watch storage boundaries, history replay, snapshot scheduling, input validation, and session transitions under the existing `API_LEVEL 3.6` baseline.

## Findings and fixes

| Priority | Reproduction and impact | Fix |
| --- | --- | --- |
| High | Deliver a history entry, edit its note/rating on the phone, then replay the original watch entry after a lost acknowledgement. Replay overwrote the phone feedback and increased the revision again. | Watch delivery now acknowledges an existing `historyId` without rewriting the canonical record. Phone feedback editing retains its normal save path. |
| High | Edit a recipe and receive watch history during the 150 ms debounce. The immediate history flush cleared the pending catalog update. | Immediate flushes merge requested slices with already queued slices. |
| Medium | Persist JSON `null` in the watch catalog or sync metadata key and restart. Startup dereferenced null and threw. | Non-object top-level values fall back to the default catalog or sync metadata. |
| Medium | Deliver `UPSERT_HISTORY_ENTRY` with a null payload. The app-side listener threw before validation. | Missing entries now reach the existing validation rejection path. |
| Medium | Validate a recipe whose steps are an object or contain null. Duration summation threw instead of returning validation issues. | Duration validation runs only after checking the collection and its entries. |
| Medium | Pass a persisted completed, aborted, or expired session to resume. The reducer could reactivate it and rewrite elapsed time. Other transitions also accepted terminal sessions. | Terminal sessions remain unchanged through resume, advance, tick, and abort. |

Ten regression cases reproduce these failures against the original implementation. They exercise real project modules with the existing mocked Zepp runtime and phone transport harness.
